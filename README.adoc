= Modular monolith example: customers and orders

This application is an example of a https://microservices.io/post/architecture/2023/07/31/how-modular-can-your-monolith-go-part-1.html[modular monolith architectural style].

## The application consists of three domain modules

It consists of three domain modules:

* `customers` - manages customers
* `orders` - manages orders
* `notifications` - sends notifications

image::./customers-and-orders-modular-monolith.png[]

## A domain module has a hexagonal architecture

A domain module has a hexagonal architecture:

* `domain` - the business logic
* `web` - an inbound adapter that implements a REST API
* `persistence` - an outbound adapter that implements database access

## Domain module collaboration mechanisms

Domains collaborate in two different ways.
The first is by one domain invoking another.
For example:

[java]
----
  @Transactional
  public Order createOrder(long customerId, Money orderTotal) {
      ...
      customerCreditService.reserveCredit(customerId, order.getId(), orderTotal);
----

`CustomerCreditService` is an interface that the `Orders` domain defines.
It describes what `Orders` needs from `Customers`.
An outbound adapter in the `Orders` domain module implements it by calling the `Customers` domain module's API, which can be either a POJO API or a gRPC API.
See <<_a_domain_module_api_can_be_a_pojo_api_or_a_grpc_api>>.

The second collaboration mechanism is the https://microservices.io/post/architecture/2023/10/30/how-modular-can-your-monolith-go-part-5-domain-observers.html[Observer pattern] - one domain subscribes to events emitted by another domain.
For example:

[java]
----
public class CustomerDomainObserverPojoAdapter implements CustomerDomainObserver {

  @Override
  public void noteCustomerCreated(CustomerInfo customerInfo) {
    customerEventHandler.noteCustomerCreated(customerInfo.customerId(), customerInfo.name(), customerInfo.emailAddress());
  }
----

`CustomerDomainObserverPojoAdapter` is in the `notifications-customer-observer-pojo-adapter` Gradle sub-project.
It's registered with the `Customers` domain module's `CustomerDomainObservers`, and calls `CustomerEventHandler`, an interface defined by `notifications-domain`.
As a result, `notifications-domain` doesn't depend on the `Customers` domain module.

The publishing side uses the same approach.
When a customer is created, `customers-domain` calls `CustomerEventPublisher`, an interface that it defines, with its own `CustomerInfo`.
`CustomerDomainObserversImpl`, in the `customers-api-observer` Gradle sub-project, implements both `CustomerEventPublisher` and `CustomerDomainObservers`.
It converts the domain's `CustomerInfo` into the observer API's `CustomerInfo`, and calls each registered observer.
As a result, `customers-domain` doesn't depend on the observer API.

Note: For simplicity, https://microservices.io/post/architecture/2023/11/13/how-modular-can-your-monolith-go-part-6-transactional-commands.html[the observers are executed in the publisher's transaction].

## A domain module API can be a POJO API or a gRPC API

The `Customers` domain module has two different versions of its credit management API:

* POJO API - the `CreditManagement` Java interface, defined by `customers-api-credit-management-pojo`
* gRPC API - `CreditManagementService`, a gRPC service defined by `customers-api-credit-management-grpc`

By default, `Orders` uses the POJO API.
When the `grpc` Spring profile is active, `Orders` uses the gRPC API.

The gRPC option uses an https://grpc.github.io/grpc-java/javadoc/io/grpc/inprocess/InProcessServerBuilder.html[in-process gRPC server], so the call stays inside the monolith's JVM.
It shows that a domain module can expose a language-neutral API, defined by a `.proto` file, without becoming a separate service.

The gRPC option consists of these Gradle sub-projects:

* `customers-api-credit-management-grpc` - the Domain API sub-project: `credit_management.proto` and the generated Java classes
* `customers-credit-management-grpc-server` - an inbound adapter in `Customers` that implements the gRPC service by delegating to `CreditManagement`
* `orders-credit-management-grpc-proxy` - an outbound adapter in `Orders` that implements `CustomerCreditService` using a gRPC blocking stub

The POJO option is implemented by `orders-credit-management-pojo-proxy`, an outbound adapter in `Orders` that implements `CustomerCreditService` by calling `CreditManagement`.

`orders-domain` depends on neither API.
It only depends on its own `CustomerCreditService` interface.
As a result, switching between the POJO API and the gRPC API doesn't require `orders-domain` to be changed, recompiled or retested.

### A gRPC call runs in the caller's transaction

The server and the client channel use `directExecutor()`, and the proxy uses a blocking stub.
As a result, a gRPC call runs on the caller's thread and joins the caller's transaction, just like a POJO API call.

The gRPC server maps exceptions to status codes:

* `CustomerNotFoundException` - `NOT_FOUND`
* `CustomerCreditLimitExceededException` - `FAILED_PRECONDITION`

The proxy throws `StatusRuntimeException` for an error status, which rolls back the caller's transaction.

### The observer API also has a gRPC version

The `Customers` domain module also has two versions of its observer API:

* POJO API - the `CustomerDomainObservers` and `CustomerDomainObserver` Java interfaces, defined by `customers-api-observer-pojo`
* gRPC API - two gRPC services defined by `customers-api-observer-grpc`:
** `CustomerDomainObserversService`, which `Customers` implements. An observer calls `RegisterObserver` with the name of its in-process gRPC server.
** `CustomerDomainObserverService`, which each observer implements. `Customers` calls `NoteCustomerCreated` when a customer is created.

By default, `Notifications` uses the POJO API.
When the `grpc` Spring profile is active, `Notifications` uses the gRPC API.

The gRPC option consists of these Gradle sub-projects:

* `customers-api-observer-grpc` - the Domain API sub-project: `customer_domain_observers.proto`, the generated Java classes and `CustomerDomainObserversInProcessServer`
* `customers-observer-grpc-server` - an inbound adapter in `Customers` that implements `RegisterObserver` by registering a `CustomerDomainObserver` that calls the observer's gRPC server
* `notifications-customer-observer-grpc-adapter` - an adapter in `Notifications` that implements `CustomerDomainObserverService` by calling `CustomerEventHandler`, and registers it at startup

The POJO option is implemented by `notifications-customer-observer-pojo-adapter`.
`notifications-domain` depends on neither API.

`Customers` calls the observer with a blocking stub and `directExecutor()`.
As a result, the observer runs in the transaction that created the customer, and an error status rolls it back, just like a POJO observer.

`Notifications` registers while the Spring application context is being created, before the web server accepts requests.
It injects a `CustomerDomainObserversInProcessServer` bean, which `Customers` defines only after its in-process server has started.
As a result, `Notifications` can't call `RegisterObserver` before that server has started.

### The notifications API also has a gRPC version

`Orders` invokes the `Notifications` domain module to send an order confirmation email.
`orders-domain` calls `NotificationSender`, an interface that it defines.

The `Notifications` domain module has two versions of its API:

* POJO API - the `NotificationService` Java interface, defined by `notifications-api-pojo`
* gRPC API - `NotificationService`, a gRPC service defined by `notifications-api-grpc`

By default, `Orders` uses the POJO API.
When the `grpc` Spring profile is active, `Orders` uses the gRPC API.

The gRPC option consists of these Gradle sub-projects:

* `notifications-api-grpc` - the Domain API sub-project: `notifications.proto` and the generated Java classes
* `notifications-grpc-server` - an inbound adapter in `Notifications` that implements the gRPC service by delegating to the POJO `NotificationService`
* `orders-notifications-grpc-proxy` - an outbound adapter in `Orders` that implements `NotificationSender` using a gRPC blocking stub

The POJO option is implemented by `orders-notifications-pojo-proxy`.

`NotificationService.sendEmail()` takes the email template's parameters as a `Map<String, Object>`.
Protobuf has no type for an arbitrary Java object, so `notifications.proto` defines them as a `map<string, string>`.
The proxy converts each value with `String.valueOf()`, for example an order id of `42` becomes `"42"`.

### Running the application with the gRPC API

Activate the `grpc` Spring profile, for example:

[source,bash]
----
./gradlew :main:bootRun --args='--spring.profiles.active=grpc'
----

`CustomersAndOrdersGrpcApplicationTest` runs the application's component tests with the `grpc` profile active.

## Minimizing build-time coupling is a key design goal

X is https://microservices.io/post/architecture/2023/09/12/how-modular-can-your-monolith-go-part-4-physical-design.html#apply-physical-design-principles-to-reduce-build-time-coupling[build-time coupled] to Y if a change to Y requires X to be recompiled and, more importantly, retested.
Since fast builds are essential, it's important to minimize build-time coupling.

This example minimizes build-time coupling in a few different ways:

* Domain module = multiple Gradle projects
* Domain modules have a Domain API Gradle sub-project
* Uses the Interface Segregation Principle (ISP) to define narrower APIs.

### Domain module = multiple Gradle projects

To reduce build-time coupling within a domain module, each domain module consists of multiple Gradle sub-projects.
Typically, the sub-projects correspond the elements of the hexagonal architecture - domain or adapter.
For example, the `Customers` domain consists of multiple Gradle sub-projects including `customers-domain`, `customers-web`, and `customers-persistence`.
An important benefit of this design is that it reduces build-time coupling.
A change, for example, to the `web` adapter doesn't require the `domain` or `persistence` adapter to be recompiled/retested.

### Domain modules have a Domain API Gradle sub-project

The `Customers` and `Notifications` domain modules - specifically their domain logic - are used by other domain modules:

* `Orders` invokes `Customers` to reserve and release credit, and invokes `Notifications` to send emails
* `Notifications` registers with `Customers` as an observer, so that it's notified when a customer is created

In order to minimize build-time coupling, each of those domain modules has a https://microservices.io/post/architecture/2023/09/12/how-modular-can-your-monolith-go-part-4-physical-design.html#using-domain-api-modules-to-reduce-build-time-coupling[Domain API Gradle sub-project], which defines that module's API.
For example, the `Customers` domain has a `customers-api` Gradle sub-project, which contains its API classes.

A domain module's clients only depend on its Domain API Gradle sub-project.
Moreover, its clients are tested using mocks of the API.
For example, the `Orders` domain is tested using mocks of `CustomerCreditService` and `NotificationSender`, which `Orders` uses to call the `Customers` and `Notifications` domains' APIs.
As a result, a domain module's implementation can be changed without having to recompile/retest its clients.

### Uses the Interface Segregation Principle (ISP) to define narrower APIs.

To further reduce build-time coupling, the `Customers` domain module uses the https://microservices.io/post/architecture/2023/09/12/how-modular-can-your-monolith-go-part-4-physical-design.html#applying-the-interface-segregation-principle-isp[Interface Segregation Principle (ISP)] to define narrower APIs.
It has five Domain Module API Gradle sub-projects:

* `customers-api` - defines CRUD operations
* `customers-api-credit-management-pojo` - defines operations for managing credit
* `customers-api-credit-management-grpc` - the gRPC version of `customers-api-credit-management-pojo`
* `customers-api-observer-pojo` - for registering observers of the `Customers` domain
* `customers-api-observer-grpc` - the gRPC version of `customers-api-observer-pojo`

As a result, each client only build-time coupled to those APIs that it's actually using.
